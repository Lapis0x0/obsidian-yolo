# MCP

MCP (Model Context Protocol) is an open protocol that lets AI plug into external services. In YOLO it works both ways:

- **Plugging others in** — let YOLO use GitHub, databases, search services and other external tools
- **Being plugged into** — let external clients like Claude Desktop use your vault

> **MCP is desktop only.** Not just the local-process type: remote HTTP / SSE / WebSocket are disabled on mobile too. The mobile settings page says so outright — "Custom tools (MCP) are not supported on mobile devices".

## Connecting to external MCP services

Where: **Settings → YOLO → Agent → Global capabilities → Tools → Manage tools**. MCP server management sits at the bottom of that dialog — click **Add custom tool server (MCP)**.

The form supports two editing modes, **Form** and **JSON**, and you can switch between them freely.

### Supported connection types

| Type | Value | What it is |
|------|-----|------|
| Local process | `stdio` | Spawns a child process on your machine |
| Remote | `http` | Streamable HTTP, with OAuth or custom headers |
| Remote | `sse` | Server-Sent Events |
| Remote | `ws` | WebSocket |

### Config examples

Local process (GitHub's official MCP as an example):

```json
{
  "transport": "stdio",
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": {
    "GITHUB_PERSONAL_ACCESS_TOKEN": "your token"
  }
}
```

Remote HTTP, authenticating with a header:

```json
{
  "transport": "http",
  "url": "https://example.com/mcp",
  "headers": {
    "Authorization": "Bearer your token"
  }
}
```

**Claude Desktop's config format works too** — paste it straight into the JSON editor and it gets recognized automatically:

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "your token" }
    }
  }
}
```

If `mcpServers` holds more than one server, you have to say which one to import in the **Name** field. With only one, the name is filled in for you.

### OAuth

Only the `http` type supports it. Pick OAuth under Authentication, click **Connect**, and YOLO opens your system browser to finish authorization. The dialog shows the status along the way (Checking... / Connecting... / Connected / Connection failed), and **you can only save once the connection succeeds**.

If you rename the server later, the saved credentials migrate with it — no need to authorize again.

### Once it's connected

Each row in the server list shows the name, the status, how many tools were discovered, and an enable toggle.

Every Agent can also control that server separately from its own **Tools** tab:

- **Disclosure mode**: **On demand** puts only the tool names in the prompt and loads the full definitions when they're actually used; **In context** carries the full definitions every turn. **For servers with a lot of tools, go with On demand**
- **Approval mode**: Full access / Require approval / Approve dangerous operations

### Two costs to keep in mind

**Token cost**: whatever an MCP tool returns goes into the model's context in full. Services that return a lot (a database query pulling a few hundred rows at once, say) will push your usage up noticeably. The Add dialog warns about this right at the top.

**Security boundary**: MCP tools run in external processes, so **they don't go through YOLO's path checks**. That means an MCP server with file access can walk right around the [workspace scope](./tools-and-permissions.md#workspace-scope-limiting-where-it-can-wander-on-its-own) limit. Only connect services you trust.

## Expose YOLO to external agents

The other direction: you can let Claude Desktop and other MCP clients use your vault.

Where: **Settings → YOLO → Agent → External agent access** (**desktop only**).

Turn on **Allow external agent access** and YOLO starts a local HTTP MCP service, on port **28124** by default (deliberately dodging the 27123/27124 that the Local REST API plugin tends to use).

The UI hands you a connection config you can paste straight into the client:

```json
{
  "transport": "http",
  "url": "http://127.0.0.1:28124/mcp",
  "headers": {
    "Authorization": "Bearer <auto-generated token>"
  }
}
```

### What gets exposed

Four tools:

| Tool | What it does |
|------|------|
| `vault_search` | Searches your vault |
| `agent_task_start` | Takes one of your configured YOLO Agents plus an instruction and dispatches the task **asynchronously**, returning a task ID immediately |
| `agent_task_get` | Checks a task's status and result |
| `agent_task_cancel` | Cancels a task |

So an external agent can do more than search your notes — it can **borrow the YOLO Agents you've already set up** to get work done.

At most four tasks run at once. The status flow is: running → (possibly) waiting for your confirmation → done / failed / cancelled / interrupted.

> "Waiting for your confirmation" means the task hit a tool that needs approval. You have to come back to Obsidian and deal with it before the task continues.

**A task is really just a normal conversation created in the background**, so once it's done you can open it in Obsidian's chat history like any other and read the whole record — it isn't a black box.

### Port and token

If the port is taken you get a pointed message about it (most often a clash with something like Local REST API); just pick another port.

The token is **generated once, the first time you turn this on** — there's no separate "regenerate" button in the UI. If you need a new one (a leaked token, for instance), turn the toggle off and back on.

## About scheduled tasks

**YOLO has no built-in scheduler or cron feature.**

What the external access above gives you is "async background tasks triggered on demand by an external system", not tasks that fire on a schedule. If you want real scheduling, you need an external tool (your system's cron, or your client's own scheduling) to call this interface on a timer.
